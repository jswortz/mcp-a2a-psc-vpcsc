### Slide 1: Executive Overview — The "What" & "Why"

* **The "What":** Gemini Enterprise (`discoveryengine.googleapis.com`) and Vertex AI Agent Runtime (`aiplatform.googleapis.com`) execute in Google-managed tenant projects outside your VPC. To reach internal MCP tools or A2A agents without public IPs, you deploy three core pillars: a **PSC Network Attachment + Internal ALB / PSC Endpoint**, a centralized **Agent Gateway + Agent Registry**, and **VPC-SC + IAM v3 / IAP v2 + Model Armor security policies**.
* **The "How" at a Glance:** Instead of opening public firewall ports, Google's tenant project injects packets privately into your consumer PSC subnet (`10.128.20.0/28`), resolves internal hostnames via Split-Horizon Cloud DNS Peering (`internal.corp.example.com.` and `run.app.`), and enforces per-tool authorization at the Agent Gateway before any packet reaches your backend.

### Slide 2: Reference Architecture — How Requests Flow: Control Plane (Registry) vs. Data Plane (PSC)

* **The "What":** Every component—across Google's tenant project and your Consumer VPC—operates inside your **VPC Service Controls (VPC-SC)** perimeter (`discoveryengine.googleapis.com`, `aiplatform.googleapis.com`, `networkservices.googleapis.com`, and `agentregistry.googleapis.com`).
* **How Agent Registry Fits In (Control Plane vs. Data Plane):** **Agent Registry** (`agentregistry.googleapis.com`) is the **control-plane catalog API** in your GCP project. It does not sit in the packet data path itself; instead, you register writable `Service` resources in Agent Registry (containing private URLs, MCP `toolspec.json` schemas, and A2A `agent-card.json` metadata), which automatically populate the read-only `mcpServers` and `agents` catalog views. When you bind **Agent Gateway** to **Agent Registry**, the gateway uses Agent Registry at runtime to verify that a target MCP server or A2A agent is approved and to evaluate IAM v3 / IAP v2 CEL rules before routing traffic over PSC.
* **The "How" (Bidirectional Data Plane Flow):**
  * **Outbound (Gemini Enterprise → Private MCP / A2A):** Gemini Enterprise (`ge-mcp-psc-vpcsc-app`) looks up the endpoint via its `REGISTRY_MCP` DataConnector (`ge-mcp-psc-collector`), evaluates **IAP v2 / IAM v3** rules at the **Agent Gateway** (`ge-private-egress-gateway`), resolves private hostnames via **Cloud DNS Peering**, and sends HTTPS traffic through the **PSC Network Attachment** (`ge-agent-psc-attachment`, IP `10.128.20.2`) to your **Internal Cross-Region ALB** (`10.128.10.50:443`) or **Global PSC Endpoint** (`172.16.20.20:443`) and backend NEGs (Cloud Run, GKE, or On-Premises via Cloud Interconnect/VPN).
  * **Inbound (Customer VPC / On-Prem → GEAP Agent Engine):** Internal callers connect privately to a **Consumer PSC Endpoint** (`ForwardingRule` IP `10.128.10.99`) targeting the `REASONING_ENGINE` Service Attachment (`*.a2a.hyperlane.ucaip.goog`).
  * **Mandatory Regional Alignment:** Deploy Agent Gateway and Agent Registry in `us-central1` for `global`/`us` Gemini Enterprise apps, or `europe-west1` for `eu` apps.

### Slide 3: Implementation (Steps 1–3) — How to Build the Private Egress Foundation

* **The "What":** Before registering any MCP server or A2A agent, you establish the private Layer-3/Layer-7 network pipe and bind the Agent Gateway to your Gemini Enterprise App.
* **The "How" (3 Sequential Steps):**
  * **Step 1 (Consumer VPC & PSC Attachment):** Create a dedicated `/28` consumer subnet (`10.128.20.0/28`) with `--enable-private-ip-google-access` (regular subnet required for `network-attachments`), create `ge-agent-psc-attachment` (`ACCEPT_AUTOMATIC`), and allow ingress from `10.128.20.0/28` to your Internal ALB VIP (`10.128.10.50`) and PSC endpoints on `tcp:443`.
  * **Step 2 (Internal ALB & Split-Horizon Cloud DNS):** Provision an `INTERNAL_MANAGED` Cross-Region ALB (`10.128.10.50:443`) or Global PSC Endpoint (`172.16.20.20:443`), create Private Cloud DNS zones (`internal.corp.example.com.` and `run.app.`) pointing to your private VIPs, and grant `roles/dns.peer` to `service-PROJECT_NUMBER@gcp-sa-networkmanagement.iam.gserviceaccount.com` and `service-PROJECT_NUMBER@gcp-sa-agentgateway.iam.gserviceaccount.com`.
  * **Step 3 (Deploy & Bind Agent Gateway):** Import your `AgentGateway` YAML (`v1alpha1`, `governedAccessPath: AGENT_TO_ANYWHERE`, `networkConfig.egress.networkAttachment`, `dnsPeeringConfig`, and `registries`) via `gcloud alpha network-services agent-gateways import`, then bind `agentGatewaySetting.defaultEgressAgentGateway` on your Gemini Enterprise App.

### Slide 4: Implementation (Steps 4–5) — How to Register & Connect MCP and A2A (Inside or Outside VPC)

* **The "What" (Where You Register vs. Where the Workload Runs):**
  * **Control-Plane Registration Is Always in Your GCP Project:** Regardless of whether your MCP server or A2A agent runs inside your VPC or outside it, you always register its catalog entry in **Agent Registry** (`gcloud alpha agent-registry services create` in `us-central1` or `europe-west1`) inside your VPC-SC-protected GCP project. That writable `Service` automatically generates the read-only `mcpServers` or `agents` view.
  * **How It Works When MCP or A2A Runs Inside vs. Outside Your VPC:** Agent Gateway **always** sends traffic into your Consumer VPC first via the **PSC Network Attachment**:
    * **Inside VPC (Cloud Run, GKE, GCE):** Reached via an in-VPC **Serverless NEG** or **Global PSC Endpoint** (Cloud Run with `INGRESS_TRAFFIC_INTERNAL_ONLY`) or **GKE Standalone NEG**.
    * **Outside VPC — On-Premises / AWS / Azure:** Your Internal ALB routes to a **Hybrid Connectivity NEG** (`NON_GCP_PRIVATE_IP_PORT`), which forwards traffic transitively over **Cloud Interconnect** or **HA VPN** to your on-premises or multi-cloud private IP:Port.
    * **Outside VPC — External Partner VPC or SaaS:** Traffic enters your VPC via the PSC Network Attachment first, then routes either to a **Consumer PSC Endpoint** (connected to a partner's PSC Service Attachment) or through your VPC's **Secure Web Proxy (SWP) + Cloud NAT** (with the FQDN allowlisted in `discoveryengine.managed.allowedEgressFqdns`).
* **The "How" for Custom MCP (Step 4):**
  * Register via `gcloud alpha agent-registry services create` with `--mcp-server-spec-type=tool-spec` (MCP `2025-03-26` Streamable HTTP JSON-RPC returning both `structuredContent` and `content`).
  * Connect to Gemini Enterprise using **Path A (Recommended):** Create a `REGISTRY_MCP` DataConnector (`use_agent_gateway_egress: true`) and grant `roles/run.invoker` to `service-PROJECT_NUMBER@gcp-sa-discoveryengine.iam.gserviceaccount.com`, or **Path B (Direct):** Custom MCP Server connector with OAuth 2.0 redirect URI `https://vertexaisearch.cloud.google.com/oauth-redirect`.
* **The "How" for A2A Agents (Step 5):**
  * **Outbound Delegation (Scenario A):** Register your `agent-card.json` (A2A `v0.3.0`) via `gcloud alpha agent-registry services create --agent-spec-type=a2a-agent-card`; Gemini Enterprise routes delegations through your bound Agent Gateway into your VPC.
  * **Inbound Invocation (Scenario B):** Create a Consumer `forwarding-rules` PSC Endpoint (`10.128.10.99`) in your VPC targeting the `REASONING_ENGINE` Service Attachment URI and map `*.a2a.hyperlane.ucaip.goog` in Private Cloud DNS.

### Slide 5: Implementation (Step 6) — How to Comply with VPC-SC & Enforce Zero-Trust Rules

* **The "What":** VPC Service Controls blocks Custom MCP connectors and IAM v3 policy bindings by default unless you follow strict perimeter ordering and enable four Organization Policies.
* **The "How" (4 Compliance Pillars):**
  * **VPC-SC Perimeter Ordering:** Place your project inside the VPC-SC perimeter (`discoveryengine`, `aiplatform`, `networkservices`, `agentregistry`) **before** creating any Custom MCP connector. Do not use OAuth Dynamic Client Registration (DCR) or static API keys inside VPC-SC.
  * **Four Mandatory Org Policies:** Set `discoveryengine.managed.disableCustomMcpServerConnector` to **Off** (`enforce: false`), add `custom_mcp` to `discoveryengine.managed.allowedDataSources`, allowlist your internal domain in `discoveryengine.managed.allowedEgressFqdns`, and set `iam.managed.disableAccessPolicyBindings` to **Off** (`enforce: false`).
  * **Fine-Grained IAM v3 + IAP v2 Tool Governance:** Import an `AuthzExtension` (`iap.googleapis.com`, `iapPolicyVersion: V2`) and `AuthzPolicy` (`REQUEST_AUTHZ`), then create and bind an IAM v3 `access-policies` rule (`ge-mcp-a2a-uap`) granting `iap.googleapis.com/resources.egressViaIAP` with split CEL rules: Rule 1 permits MCP handshake/discovery (`destination.is_registered == true && request.mcp.method != 'tools/call'`), and Rule 2 restricts `tools/call` to approved read-only tools (`request.mcp.tool.name == 'query_financial_metrics'`).
  * **Runtime Defense & Verification:** Enable **Vertex AI Model Armor** floor settings (`INSPECT_AND_BLOCK`) to block indirect prompt injection and PII/secret leaks, confirm PSC `ACCEPTED` status, and audit `egressViaIAP` entries in Cloud Audit Logs.
